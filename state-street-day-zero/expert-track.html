How this track works

The job is 75% product leadership and delivery, 25% client and stakeholder engagement. Expertise here means two things: you can read and question any data artefact your teams produce, and you can design the four capabilities the JD names. Each module is built the same way.

Why the JD asks

Which line of the posting the module serves, and what the hiring manager is really checking.

Install

Exact download and setup steps for the tool, Windows and macOS, free tier or trial wherever one exists.

Lab

A hands-on exercise in your repository. Every lab uses one dataset: a fictional custodian's clients, positions, trades, corporate actions, NAVs, and the Digital Experience tables for users, entitlements, alerts, documents and report runs.

Ladder

Three rungs. Conversant means you can follow a meeting and ask one sharp question. Practitioner means you can do the thing yourself on the lab. Expert means you can design it, govern it and teach it.

Proof

An artefact you leave behind: a query, a dashboard link, a diagram, a one-page decision. Proof is what you show a stakeholder or an interviewer, and what convinces you that you know it.

03

SQL and data modelling

SQL is the first tool the posting names and the one that unlocks every other module. You will read far more SQL than you write, but writing it on the lab is the fastest way to learn to read it.

Install

Zero install: Python's built-in SQLite runs the whole lab. Real server: PostgreSQL 16 via winget install PostgreSQL.PostgreSQL.16 on Windows or brew install postgresql@16 on macOS, or docker compose up -d in the lab folder. Client: DBeaver Community from dbeaver.io connects to all of them, plus Snowflake, Athena and RDS. Full steps are in the Day Zero briefing, Step 06.

Lab

The lab has fifteen tables. Five dimensions, five custody facts, and five Digital Experience tables that model the JD's capabilities: users, entitlements, alerts, documents and report runs. Twenty queries, each labelled with the screen it powers.

python3 sql-lab/run_sqlite.py             # all 20 queries
python3 sql-lab/run_sqlite.py 14 15 16 17 18 19 20   # the Digital Experience set
python3 sql-lab/run_sqlite.py --shell     # write your own

Then write these five yourself, in the shell, without looking at the answers:

  1. Every user who can INSTRUCT on any Meridian account, with their MFA status.
  2. Alerts per user, ordered by unacknowledged count, for CRITICAL only.
  3. For each document type, the share opened within 24 hours of publication. (Hint: compare timestamp strings, or do it in Python in Module 04.)
  4. Report runs per report name split by run type, as a pivot using CASE.
  5. The DX scorecard (Q20) rewritten with JOINs and GROUP BY instead of subqueries.
Data modelling

Open sql-lab/schema.sql. For each fact table, say the grain aloud. Then design one new table for a capability the lab lacks: user subscriptions (which user wants which alert types on which channels, with quiet hours). Decide the grain, the keys, the dimension it needs, and which existing query changes because of it. Write the CREATE TABLE, add three rows to the seed, and rewrite Q16 to use it.

Rules of good modelling you can apply in any review: one grain per fact table; facts are numeric and additive; dimensions carry the vocabulary; surrogate keys, never business identifiers that get reused; every client-facing table has an entitlement path; every row has a load timestamp.

Ladder
ConversantReads SELECT, JOIN, WHERE, GROUP BY, HAVING. Asks about grain, join keys, date filters and entitlements in a review.
PractitionerWrites multi-join aggregates, CASE pivots, window functions (RANK, LAG, running sums), CTEs. Can design a fact and dimension table from a screen.
ExpertReasons about performance and cost (columnar scans, partition pruning), sets data SLAs, defines marts, and can spot double counting from the grain alone.
Proof

Your five queries and the new subscriptions table committed to the repo, plus a one-paragraph note: "what this model can and cannot answer".

05

Snowflake and Sigma

Snowflake is the data platform named in the posting, and Sigma is a BI tool built to sit on it. Together they are the "modern data management" the skills list refers to. Both have free trials that are enough to become a practitioner.

Install
  1. Snowflake: signup.snowflake.com, Standard edition, cloud AWS, pick the region nearest you. Thirty days and 400 dollars of credits. Snowsight, the web UI, is the whole tool; nothing to install. Optional: pip install snowflake-connector-python for Python.
  2. Sigma: sigmacomputing.com, free trial. During setup, connect it to your Snowflake trial account (Admin, Connections, Snowflake: account identifier, a user, a warehouse). Sigma then browses your tables in a spreadsheet-like interface.
Lab

Follow sql-lab/aws/README.md, Exercise 3, and sql-lab/aws/snowflake.sql. In order:

  1. Create a tiny warehouse with 60-second auto-suspend. Cost governance is a habit from the first minute.
  2. Paste the schema, paste the seed, run all twenty queries unchanged. Note Snowflake's native version of Q11 with QUALIFY.
  3. Create a secure view filtered to one client. That view is what Secure Data Sharing shares: the client queries it live, nothing is copied, and entitlements live in the data layer.
  4. Run the Time Travel and zero-copy clone lines. Explain to yourself why "we cannot reproduce what the client saw" is no longer an acceptable incident answer.
  5. Check credits used in the account usage view. Then leave the warehouse running overnight by mistake, on purpose, and check again. That number is the cost-governance conversation.
  6. Optional, the real-world path: export CSVs, put them in an S3 bucket, and load with COPY INTO from an external stage.

Sigma: open the connection, drag FACT_ALERTS into a workbook, group by alert type and severity, add a calculated column "Acknowledged" as acknowledged_at is not null, and build the Q16 table without writing SQL. Then open the SQL Sigma generated. That is the whole point of the tool: business users make governed tables into analyses, and you can inspect what they did.

What to know cold
  • Storage and compute are separate. Warehouses are independent compute clusters that suspend when idle; storage is one shared copy.
  • Isolation is free: the overnight ELT warehouse can never slow the client-API warehouse.
  • Cost is behavioural: auto-suspend, resource monitors, statement timeouts, tagging and monthly review.
  • Secure Data Sharing replaces nightly SFTP files with live, governed, revocable access. Premium channel, not an immediate replacement for every client.
  • Time Travel and cloning come from immutable storage, which is why they are cheap.
Ladder
ConversantCan explain the architecture and why it changes economics, and knows what a share, a secure view and a warehouse are.
PractitionerHas loaded data, run queries, built a secure view, read a cost report, and connected a BI tool.
ExpertCan propose a data-sharing product with pricing and design partners, set per-mart SLAs, and run a cost-governance review that finds 20 to 30 percent.
Proof

A screenshot of the secure view's results as a second role, and a one-page "Snowflake data delivery product" proposal: audience, what is shared, entitlement model, SLA, price basis, risks.

06

Tableau and visualisation

"Intuitive, data-driven visual experiences" is the posting's phrase for what your screens are. Tableau is where you learn the craft fast, because every chart is a decision about what a client should notice first.

Install

Tableau Public (free, full authoring, file sources only, publishes to a public profile so never use real data) or Tableau Desktop (14-day trial, connects to PostgreSQL and Snowflake). Both from tableau.com. Windows and macOS installers; no command line.

Lab

tableau/BUILD.md is a sheet-by-sheet recipe for a seven-sheet Digital Experience dashboard: fails board, deadline calendar, alert funnel, time to acknowledge, documents nobody reads, self-service ratio, entitlement review. Data comes from one script:

python3 tableau/export_flat.py     # seven wide CSVs into tableau/data/

Build it, add a client filter that applies to every sheet, publish to Tableau Public, and send yourself the link. Then the harder exercise: delete two sheets. Decide which two a client operations analyst would not miss at 08:00, and write down why.

Principles
  • Exceptions first. The screen's top-left answers "what needs me now".
  • One number, one definition. Every calculated field in Tableau must match the glossary in Module 07.
  • As-of date on every view. A number without its business date is a dispute waiting to happen.
  • Tables are not failures. Institutional users want dense, sortable, exportable tables; charts summarise, tables act.
  • Colour means state (critical, warning, good), not decoration.
  • Governed self-service: analysts build on certified data sources; nobody builds on a private extract of positions.
Ladder
ConversantCan critique a dashboard: what is the question, what is the as-of, what is the definition, what would the user do next.
PractitionerBuilds calculated fields, filters, parameters and a multi-sheet dashboard with actions, and publishes it.
ExpertSets BI governance: certified sources, extract refresh policy tied to usage, embedded analytics in the portal, and a rule for when a dashboard becomes a product feature.
Proof

Your Tableau Public link and a paragraph on the two sheets you removed.

07

Collibra and data governance

Collibra has no free download, so this module teaches the artefacts Collibra manages by making you build them by hand, then points you at the free courses. In a G-SIB, governance is not hygiene; a client-facing number without lineage is a regulatory finding.

Install
  1. Collibra University (university.collibra.com): free account, self-paced courses. Take "Collibra Fundamentals" and the Data Governance and Data Quality tracks. Six to eight hours total.
  2. Open-source stand-in to see a catalogue UI: OpenMetadata quick start with Docker (docs.open-metadata.org, "Quickstart"). Ingest the lab's PostgreSQL database, then add glossary terms and owners to the tables.
Lab

The governance/ folder is a governance pack for the Digital Experience domain, the same four artefacts Collibra holds:

  • glossary.csv: eighteen business terms with definition, owner, steward, golden source and related columns. Note that you are the named owner of every Digital Experience term.
  • data_dictionary.csv: the catalogue entries, with a PII flag and a DQ rule per column.
  • dq_rules.sql and run_dq.py: thirteen data-quality rules as queries that return violations. Run them:
python3 governance/run_dq.py       # scorecard, and a publish-or-hold decision

The run finds a blocking failure (a cross-client entitlement) and three warnings (late feed, undelivered SMS, grants with no expiry) and says HOLD. Decide whether you agree with the severity of each rule, change one, and rerun. Then read lineage.md and do its exercise: draw the lineage for "acknowledged alert rate" and find the upstream change that would silently break it.

What to know cold
  • Roles: owner (accountable executive), steward (day-to-day), custodian (technology), council, CDO office.
  • Six quality dimensions: completeness, accuracy, timeliness, consistency, validity, uniqueness.
  • Block versus warn: a missing account is invisible until it burns someone, so completeness blocks; a late feed is visible, so it warns with a status.
  • Lineage answers the examiner's question "show me how this number was produced".
  • BCBS 239 is the regulatory root of all of this for a G-SIB.
Ladder
ConversantKnows what a glossary, catalogue, lineage graph and DQ score are, and who the owner and steward of a domain are.
PractitionerHas written definitions, DQ rules and a lineage diagram for a real metric, and can run a governance workflow in a catalogue tool.
ExpertOperates as a first-line data owner: sets the SLA sheet, chairs the domain's DQ review, defends definitions in a client dispute, and produces audit evidence on demand.
Proof

Your amended DQ rule with the reasoning, and the lineage diagram for acknowledged alert rate.

08

The four capabilities

The Function paragraph names them: IAM, alerts and notifications, document management, self-service reporting. Each one below is a product brief you should be able to write from memory, with its data model, its metric and its classic failure, all of which exist in the lab.

Identity and Access Management

Capability

Who a client user is (federated through the client's identity provider, or credentials we issue), what they may see or do per account (VIEW, INSTRUCT, ADMIN), who may grant it (delegated client administrators), and how it is recertified. Scalable and centralised means one identity service for every portal and API, not one per platform.

Data

dim_user, fact_user_entitlements. Q14 is the entitlement review screen; Q15 is the findings report every access review produces.

Metrics

Federated share of users; privileged users without MFA (target zero); grants with no expiry; recertification completion; time from access request to grant.

Classic failure

Q15 finds a relationship manager who granted herself VIEW on another client's account. Cross-client access is a security incident and a client-trust event. The control belongs in the entitlement service, which must refuse a grant where the user's client and the account's client differ.

Design questions

Federate or issue? Per-account or role-based grants? Who approves an ADMIN grant? How does an API key inherit a user's entitlements? Where is the filter applied: in every query, or in a shared entitlement service the queries call?

Alerts and Notifications

Capability

A single framework: events in (fail, deadline, NAV delay, cash shortfall, document published), subscription and entitlement resolution, channel delivery (portal, email, SMS, webhook), acknowledgement, and escalation when ignored. Intelligent alerting means dedupe across channels, quiet hours, severity-based escalation, and suppression of alerts nobody acts on.

Data

fact_alerts. Q16 is effectiveness by type; Q17 is the escalation list. The Python lab adds time-to-acknowledge and channel effectiveness. The process model in Module 10 is the sequence diagram.

Metrics

Actionable-alert acknowledgement rate; median and p90 time to acknowledge for CRITICAL; delivery failure rate per channel; alerts per user per day (the spam number); escalations that reached a second person.

Classic failure

Q17: the Halcyon tender offer had three alerts, zero acknowledgements, and defaulted with 2.7 million dollars at stake. Delivery worked. Attention failed. The fix is a process control: escalate to a named second user, then the relationship manager, before the deadline, and require acknowledgement for CRITICAL.

Design questions

What counts as acknowledged? Who owns the subscription defaults? How does a webhook client acknowledge? What is suppressed when a fail resolves itself? How do you prove to an auditor that an alert was sent and seen?

Document Management

Capability

Generation of statements, confirmations, notices, NAV packs, tax and fee documents; publication to entitled users; search and collaboration; retention and legal hold; alignment to the enterprise content platform so there is one repository, not one per product.

Data

fact_documents. Q18 is documents nobody reads; the Python lab adds hours from publish to first open.

Metrics

Publish-to-open time for notices; never-opened rate by type; documents generated but not published (the pipeline gap); retention compliance; search success rate.

Classic failure

Q18: the tender notice behind the defaulted election was published and never opened. Published is not read. A notice with a deadline and money at stake needs an alert, an acknowledgement, and a visible "unread" state on the portal home page.

Design questions

Where does generation happen and where is the record of truth? What may never be deleted and who can place a legal hold? How do clients collaborate on a document without creating uncontrolled copies? What is the content platform standard you must align to?

Self-Service Reporting

Capability

Clients run, schedule, customise and export reports and queries on their own data, in the portal and via API, instead of asking the service desk. Self-service also means transparency: the as-of date, the freshness status and the definition are visible next to the number.

Data

fact_report_runs. Q19 is the self-service ratio; Q20 is the scorecard.

Metrics

Self-service ratio per client (target agreed in the QBR); service-desk minutes spent running reports; scheduled report failures; export formats used; p95 report duration.

Classic failure

Q19: Halcyon's ratio is 25 percent. Their analyst asks the desk for the same settlement report daily. Either the report is missing, hard to find, untrusted, or the user was never onboarded. The answer is a conversation, then a number that moves.

Design questions

Which reports cover 80 percent of desk requests? What can a client customise without creating a private definition? How do scheduled reports fail loudly? How does the same report exist in the portal, the API and the data share with one definition?

Unifying thread. All four capabilities read the same identity, the same events and the same marts. That is what "unified client experience" is underneath the screens, and why the modules on SQL, Snowflake and governance come first.

Micro front-ends

The experience list ends with "micro front-end frameworks". It is there because unifying fragmented platforms is done by composing independently deployable pieces behind one shell, not by rewriting everything at once.

Install

Nothing for the demo. For the real frameworks: Node.js LTS from nodejs.org, then npx create-mf-app for Module Federation or npx create-single-spa for single-spa. VS Code for editing.

Lab
cd state-street-day-zero/microfrontend-lab
python3 -m http.server 8080          # open http://localhost:8080/shell/

The shell owns identity, routing and design tokens. Two widgets, alerts and documents, are separate Web Components with no shared code except the tokens file. Switch the signed-in user and both re-render; navigate and they lazy-load; acknowledge an alert and the state lives inside the widget. Then: add a third widget, dx-reports, that lists the signed-in user's recent report runs. Copy the documents widget, change the data and the table, register it in the shell.

What to know cold
  • Shell versus remotes; who owns the shell decides the estate.
  • Design tokens are the styling contract; versioning them is a product decision.
  • Module Federation loads separately built bundles at runtime; single-spa mounts framework-mixed apps; Web Components are the native minimum.
  • Error boundaries: a broken remote must not take down the page.
  • Shared data: two widgets needing positions should read one client-side store, not fetch twice.
  • Strangler fig: new widgets replace legacy pages one route at a time.
Ladder
ConversantCan explain shell, remote, tokens and why this is how you unify fragmented platforms.
PractitionerHas added a widget to the demo and scaffolded a Module Federation host and remote.
ExpertCan set the estate's rules: shell ownership, token versioning, testing the composed page, performance budgets, and the migration sequence.
Proof

Your third widget in the repo and a half-page "portal composition standard" with the five rules you would enforce.

Process modelling and Agile

"Business and system process modelling" and "Agile or hybrid delivery" are how the work gets specified and shipped in a regulated bank. Models find the broken step; the delivery model gets the fix through the gates.

Install
  • BPMN: demo.bpmn.io in the browser, nothing to install. Camunda Modeler (desktop, free) for saved files. draw.io has a BPMN shape library.
  • Sequence and flow diagrams: Mermaid renders on GitHub; the VS Code Markdown Preview Mermaid extension shows it live.
  • Agile tooling: Jira free tier (up to ten users) at atlassian.com. Confluence free tier for the decision log.
Lab

process-models/README.md has two models: the corporate-action election as a cross-organisation business process, and the alert lifecycle as a system sequence. Both are annotated with where the lab data shows the process breaking. Do the three exercises: redraw the election in real BPMN with a timer boundary event, model the document lifecycle, and model IAM onboarding with the point where Q15's findings would have been caught.

Agile: in a free Jira project, create four epics, one per capability, and under "Alerts" write six stories from Module 08's design questions, each with acceptance criteria that name a query or a metric. Then add the hybrid part: a "Change record" issue type with the gates a regulated release needs (risk review, access review, rollback plan, evidence).

What to know cold
  • BPMN basics: pools and lanes, tasks, gateways, timer and message events.
  • System modelling: sequence diagrams for request flows, state diagrams for lifecycles.
  • Scaled agile vocabulary: increment planning, features and stories, dependencies, definition of done that includes controls.
  • Hybrid means iterative build with waterfall-style release gates; you plan for both.

Storytelling and stakeholders

The 25 percent, and the part that decides whether the other 75 percent lands. "Present updates to senior stakeholders", "consultative mindset", "storytelling and client engagement", "stakeholder management in matrixed organisations". These are practised, not read.

Material

Bootcamp Days 14, 23, 25 and 26. The Day Zero briefing's question bank.

Lab

Write three documents, each one page, from the lab data:

  1. An executive update on the alerts capability. First line is the answer: "Actionable alerts are acknowledged 33 percent of the time; one missed election cost a client 2.7 million dollars; we will require acknowledgement and add escalation by the next increment." Then evidence (Q16, Q17), then the ask.
  2. A client story for Halcyon's QBR: what their analysts do today (the service desk runs their reports), what changes, what the number will be in a quarter, what you need from them (user onboarding).
  3. A stakeholder map for the four capabilities: for each of Product, Operations, Technology, Architecture, Enterprise Data, Risk and Client Coverage, what they want from you, what you need from them, and the forum where you meet.

Then say the executive update aloud in under ninety seconds. Time it.

Rules
  • Answer first, then evidence, then the ask. Never the journey.
  • Every story has a number, a client and a date.
  • Two versions of every data explanation: one for the operations manager, one for the engineer.
  • Write decisions down: what, why, who, when, what would change it.
  • In a matrix, forums beat escalations. Create the prioritisation forum before you need it.
Ladder
ConversantCan give a status update that leads with the answer.
PractitionerRuns a QBR segment, keeps a decision log, and has a stakeholder map that is current.
ExpertIs the person executives ask to explain the data, clients ask for the plan, and partners ask to arbitrate.
Proof

The three one-pagers in the repo. Redo the executive update after your first real month with real numbers.
