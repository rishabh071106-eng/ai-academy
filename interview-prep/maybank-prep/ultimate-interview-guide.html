1 · Why diagrams, and what interviewers look for

You said an interviewer once asked whether you can draw a system design diagram. Here's the reassuring truth: they're not testing whether you can draw pretty boxes. They're testing whether you can take a messy real-world problem and organise it into clear parts and clear connections. That's a thinking skill, and it's learnable in an afternoon.

In plain words: what a design diagram is

A system design (architecture) diagram is just a map of a software system. It answers two questions: “What are the pieces?” (boxes) and “How do they talk to each other?” (arrows). That's genuinely all it is. Everything else is detail.

What a good diagram shows the interviewer
  • You can break a big thing into parts (decomposition).
  • You understand how parts communicate (and when to use which method).
  • You think about the non-obvious things: security, scale, what can fail.
  • You can explain it out loud so a non-expert follows along.

2 · The shapes — your visual alphabet

Like letters make words, a few shapes make any diagram. Use them consistently: the same kind of thing always gets the same shape.

3 · How connections work

The arrows matter as much as the boxes. Every arrow should tell the reader three things — train yourself to always say all three out loud:

An arrow shows…By…Example
Direction — who starts the conversationwhich way the arrowhead pointsApp → Core (the app asks the core)
Type — wait for a reply, or not?solid line vs dashed linesolid = ask & wait · dashed = send & move on
What & how — the method + purposea short text label“REST/HTTPS – get balance”
In plain words: synchronous vs asynchronous

Synchronous = the caller asks and waits for the answer, like a phone call. Use it when you need the reply now (check a balance, approve a payment, return a credit decision the customer is waiting for).

Asynchronous = the caller sends a message and moves on, like a text/WhatsApp. Use it for things that can happen in the background (send an SMS, update analytics, tell another system “a loan was booked”). These usually travel through a queue / event stream (e.g. Kafka).

Say this — it scores points

“I use synchronous calls when the user is waiting on the answer, and asynchronous events for background work — that decoupling keeps the core stable and the app fast.” Knowing when to use each is what separates a strong candidate from someone who's just memorised words.

Common labels (the “how”): REST/HTTPSgRPCevents (Kafka)SQLSFTP file batchISO 20022 (payments)

4 · The 8-step method

Run these steps in order, out loud, and you'll never freeze at a whiteboard again.

  1. Clarify the problem first. What must it do? And the “-ilities”: how many users, how fast, how available, how secure, and what compliance (BNM, PCI, PDPA, Shariah)? Saying these before drawing is half the score.
  2. Put the actors & outside systems at the edges. Users on the left; external systems (CCRIS, CTOS, PayNet) on the right.
  3. List the main parts by what they do. “Origination”, “Credit decisioning”, “Pricing”, “Servicing”. One box = one job.
  4. Add the data stores. Each part that remembers things gets a database (cylinder).
  5. Stack them in layers. Channels → Security edge → Services → Integration → Core → Data. Layers reveal the flow.
  6. Draw & label every connection. Direction + type + purpose. No bare arrows.
  7. Mark the security boundary. A dashed box around the “outside-facing” zone; note where login/MFA and encryption sit.
  8. Walk one journey through it & tidy up. Trace “a customer applies → …” and check every hop exists. Add a legend. Done.

5 · Zoom levels (the C4 idea)

Professionals draw at different zoom levels depending on the audience — a model called C4. Mentioning it makes you sound senior.

LevelZoomShows
1 · ContextFurthest outThe whole system as one box, plus who/what it talks to. Great for non-technical stakeholders.
2 · ContainerCloserThe apps, services and databases inside. This is the level you'll usually draw in an interview.
3 · ComponentInside one boxThe parts within a single service.
4 · CodeClosestClasses/functions. Rarely drawn by hand.

6 · Guided practice: build one live

Let's draw a diagram together for a realistic prompt, the way you would on the day. Prompt: “Design a digital home-financing application for the MAE app.” Follow the 8 steps:

  1. Clarify: “So we want customers to apply for home financing in-app, get a decision in minutes, fully compliant with BNM and PDPA, available 24/7, secure. Peak maybe thousands of applications a day.” (You just earned marks before drawing anything.)
  2. Edges: Actor = the customer on MAE. Externals = CCRIS, CTOS, MyKad (e-KYC), the core banking system, PayNet.
  3. Parts by job: Origination (runs the journey), e-KYC, Credit decisioning, Pricing, Document service, Notifications.
  4. Data: an application database; later, a data warehouse for reporting.
  5. Layers: Channel (MAE) → Edge (gateway + login) → Services (the six above) → Integration (event bus) → Core banking → Data.
  6. Connect & label: MAE →(HTTPS) Gateway →(REST) Origination →(REST) Decisioning →(API) CCRIS/CTOS; Origination →(event) Notifications; Core →(CDC) Warehouse.
  7. Security boundary: dashed box around gateway + login; that's where the outside world meets the inside.
  8. Walk it: “Customer taps Apply → passes the gateway after MFA → Origination calls e-KYC (MyKad) and Decisioning (CCRIS+CTOS, computes DSR) → Pricing returns a rate → on accept, it books to Core → an event tells Notifications to SMS the customer.” Every hop exists. ✔
The secret

Notice you didn't need to memorise an answer — you ran a method. The same 8 steps work for any prompt they give you (a payments system, a collections tool, a deposit-onboarding flow). Learn the method, not a picture.

8 · SQL — the mental model + a banking schema

The JD asks for basic SQL. As a PO you won't write production queries, but you'll read them, ask analysts for data, and sanity-check numbers. That's very learnable.

In plain words: what SQL is

SQL (“Structured Query Language”) is how you ask a database questions. Data lives in tables — like spreadsheets, with rows (records) and columns (fields). Tables link through keys: a primary key (PK) uniquely names each row; a foreign key (FK) points to another table's PK. SQL is just a polite way of saying “show me the rows where…”.

Our toy schema (a loans database):

TableColumns
customerscustomer_id (PK), name, income
loansloan_id (PK), customer_id (FK), product, outstanding, rate, status, months_in_arrears
paymentspayment_id (PK), loan_id (FK), paid_on, amount

9 · The clauses, joins & aggregates

Six clauses do 90% of everything. Read this query like an English sentence:

-- "Show me, per product, how many active loans and total owed, biggest first."
SELECT   product, COUNT(*) AS num_loans, SUM(outstanding) AS total_owed
FROM     loans
WHERE    status = 'active'          -- filter rows
GROUP BY product                    -- one result row per product
ORDER BY total_owed DESC           -- sort
LIMIT    10;                         -- keep top 10
ClauseDoes
SELECTwhich columns to show
FROMwhich table
WHEREfilter rows (=, >, IN, BETWEEN, LIKE, IS NULL)
GROUP BY + COUNT/SUM/AVGroll many rows into summaries
ORDER BYsort the results
LIMITcut to the top N

JOIN — gluing tables together

-- Put each customer's name beside their loans
SELECT c.name, l.product, l.outstanding
FROM   customers c
JOIN   loans l ON l.customer_id = c.customer_id;

INNER JOIN = only matches in both tables · LEFT JOIN = all of the left table + matches (blanks where none — e.g. “all customers, even those with no loan”).

10 · Practice questions (with answers)

Cover the answers and try first. Getting the shape right matters more than perfect syntax.

Q1 — easy

“List all loans that are 3+ months in arrears, biggest balance first.”

SELECT loan_id, outstanding, months_in_arrears
FROM   loans
WHERE  months_in_arrears >= 3
ORDER BY outstanding DESC;
Q2 — aggregate

“Total amount owed, per product.”

SELECT product, SUM(outstanding) AS total
FROM   loans
GROUP BY product;
Q3 — the impressive one

“What % of each product's book is impaired (3+ months late)? — the GIL ratio.”

SELECT product,
       SUM(CASE WHEN months_in_arrears >= 3 THEN outstanding ELSE 0 END)
       / SUM(outstanding) AS gil_ratio
FROM   loans
GROUP BY product;
If asked SQL live, say this

“I'd GROUP BY product, SUM the outstanding, and join loans to customers on customer_id. For the impaired share I'd use a CASE inside the SUM.” Showing you can shape the query is the whole point.

Worth knowing the names of: DISTINCT, HAVING (filter on an aggregate), CTE (WITH … AS), window functions (ROW_NUMBER() OVER(...)), and DDL/DML (CREATE/INSERT/UPDATE/DELETE vs SELECT).

11 · The loan lifecycle, the easiest way possible

The simplest way to hold the whole thing in your head: a loan has a beginning (getting it), a middle (paying it), and an end (finishing it). Nine stages, but only three ideas.

PhaseStageIn one line
Getting it1 · ApplyCustomer asks; bank collects info & checks ID (KYC).
2 · Credit checkCan & will they repay? (5 Cs, DSR, CCRIS/CTOS) → a risk rating.
3 · Approve & priceYes/no, and the rate (risk-based: SBR + spread).
4 · Sign & disburseSign the promise, register collateral, pay the money out.
Paying it5 · ServicingMonthly instalments; each splits into interest + principal.
If it goes wrong6 · DelinquencyMissed payments; bank chases (collections).
7 · RehabilitationRestructure/reschedule to keep them paying (R&R, AKPK).
8 · RecoveryLast resort: sell the collateral (foreclosure/repossession).
Finishing it9 · SettlementFully paid; collateral released; closed — a gold star on credit.
The 10-second version for the interview

“Apply → credit-check → approve & price → disburse → repay → and if there's trouble: chase → restructure → recover; otherwise → settle. Most loans only ever touch the beginning, middle and end.” Islamic version: say financing not loan, profit not interest.

Want the deep, story version? See your companion guide “Lending & Pricing, Explained Like a Story” — it walks one borrower through all nine stages with worked pricing numbers.

The one distinction that explains them all

Secured vs unsecured (is there collateral?) and term vs revolving (a fixed payoff schedule, or an ongoing credit line?). Almost every product above is just a combination: a mortgage is secured + term; a credit card is unsecured + revolving; an overdraft is secured-or-not + revolving. Master these two axes and the whole catalogue makes sense.

14 · Conventional ↔ Islamic, and how the lifecycle bends

ConventionalIslamic equivalentContract used
Home loanHome financing-iMusharakah Mutanaqisah (diminishing partnership) / Commodity Murabahah
Car loan (Hire Purchase)Hire Purchase-iAITAB (Al-Ijarah Thumma Al-Bai — lease then buy)

BondSukukVarious (Ijarah, Murabahah…)

How the lifecycle bends by product type:

  • Secured loans (home, car) add steps: valuing the collateral, registering the lien, and — if it goes bad — repossession/foreclosure.
  • Unsecured loans (personal, cards) skip collateral but price higher (no asset to recover), and go straight to charge-off if they fail.
  • Revolving products (cards, overdraft) don't really “end” — the customer borrows and repays continuously within a limit.
  • Islamic products follow the same nine stages but every product needs Shariah Committee approval and uses profit, not interest.

15 · The technology landscape

You asked to cover “all the technical aspects.” Here's the whole stack a banking PO should be able to talk about — top (what customers touch) to bottom (where money is recorded).

LayerWhat it is, in plain words
ChannelsThe apps customers use — MAE, Maybank2u, ATMs, branch screens.
Edge & securityThe “front door” — a gateway that routes traffic, a firewall (WAF), and login/MFA that checks who you are.
MicroservicesThe business logic, split into small independent services (origination, pricing, servicing…) instead of one giant program.
IntegrationThe “plumbing” connecting everything — an API layer plus an event stream (Kafka) for async messages.
Core bankingThe master record-book — accounts, loans, the general ledger. The system of record.
Data & analyticsWarehouses/lakes that copy data for reporting, dashboards (MIS) and risk models.
In plain words: “microservices” & “event-driven”

Microservices = building software as many small, independent pieces that each do one job, rather than one huge block. Easier to change one piece without breaking the rest. Event-driven = pieces talk by announcing events (“a loan was booked!”) that others react to, instead of calling each other directly. This is exactly the “modern, event-driven architecture” MBB Labs says it builds — so knowing these two words is gold.

16 · Integration, APIs & events

In plain words: “API”

An API (Application Programming Interface) is a menu one system offers to another. Just like you order from a restaurant menu without seeing the kitchen, the MAE app calls the core's API to “get balance” without knowing how the core works inside. APIs are how modern banks let the friendly apps talk safely to the serious core.

TermPlain meaning
REST / HTTPSThe most common way apps call APIs over the web. Synchronous (ask & wait).
Webhook / eventA system pushes a message when something happens (async).
Kafka / event streamA high-speed “conveyor belt” of events many systems can read.
ESB / API gatewayMiddle layer that routes, secures & throttles all this traffic.
IdempotencyA safety trick so a repeated message (e.g. a retried payment) isn't processed twice. Crucial for money.
ISO 20022 / ISO 8583Standard “languages” for payments and card transactions.
Say this

“Customer-facing apps talk to the core through APIs, and services coordinate through events so they stay loosely coupled. For anything touching money I'd insist on idempotency so a retry never double-charges.”

17 · Data, MIS & analytics

The JD stresses “functional design from data capture to MIS” and “data visualization.” Here's the chain, simply:

Capture the right data points → Store (DB) → Copy out (ETL/CDC) → Warehouse / lake → Dashboards (MIS / BI)

TermPlain meaning
Data point / data dictionaryAn exact field you capture (e.g. income, collateral value) and its definition. If you don't capture it, you can't report on it.
OLTP vs OLAPThe live system that runs the bank (transactions) vs the system that analyses it (reporting). You separate them so reports don't slow the live system.
ETL / CDCHow data is copied from live systems into the warehouse (Extract-Transform-Load; or Change-Data-Capture, which streams changes as they happen).
Data warehouse / lakeBig stores of copied data for analysis. (Warehouse = tidy & structured; lake = raw & flexible.)
MIS / BIManagement Information System / Business Intelligence — the reports & dashboards leaders use to decide. Tools: Power BI, Tableau, Qlik.
The right chartTrend → line; compare → bar; funnel/drop-off → funnel; status vs target → KPI card.
The PO insight worth repeating

“Design the report you'll need first, then work backwards to the data points to capture. Reporting fails when nobody captured the field at the start.”

18 · Security, cloud & delivery (DevSecOps)

TopicWhat a PO must know
PCI DSSThe rulebook for handling card data: tokenise card numbers, never store the CVV, encrypt everything, isolate the card environment. Minimise what touches real card data.
EncryptionScrambling data so only authorised systems can read it — “at rest” (stored) and “in transit” (moving).
IAM / MFAIdentity & Access Management; Multi-Factor Authentication (password + OTP). Controls who can do what.
KYC / AMLVerify identity; screen for money-laundering & sanctions; file suspicious-activity reports. Bake it into the product, don't bolt it on.
PDPAMalaysia's data-protection law — capture consent, minimise data, protect it.
CloudRenting computing from providers (AWS/Azure/GCP) instead of owning servers — scales up/down on demand. Banks adopt it carefully for regulatory reasons.
CI/CD & DevSecOpsAutomated building, testing & releasing of software — with security built in from the start. MBB Labs explicitly runs a DevSecOps culture.
NFRs“Non-functional requirements” — scalability, availability (uptime), latency (speed), resilience. The qualities besides features.
Say this

“For a banking product I treat security and compliance as design inputs — PCI for cards, PDPA for data, KYC/AML for onboarding — and I care about the non-functionals (uptime, latency, resilience) as much as the features, because trust is the product.”
