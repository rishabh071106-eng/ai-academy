🧱 Magento / Adobe Commerce Core — Model Answers

Architecture & customisation

Plugins vs Observers vs Preferences — when do you use which? (Asked in ~every senior interview)
"My order of preference is: plugin first, observer for event-driven side-effects, preference as a last resort.

A plugin (interceptor) wraps a public method of a class — before to modify inputs, after to modify the result, around only when I must control whether the original runs at all, because around hurts performance and stack readability. Plugins are declared in di.xml with a sortOrder, and multiple modules can plug the same method safely — that's why it's the most upgrade-safe option.

An observer listens to an event via events.xml — right when I want to react to something happening (order placed → notify ERP) without changing the behaviour itself.

A preference replaces a class entirely in DI — it's a global override, only one module can win, and it breaks easily on upgrade, so I only use it when there's no public method to intercept and no event."

Follow-up they may ask — plugin execution order: for multiple plugins, all before run by ascending sortOrder, then around wrap like an onion, then all after run. Plugins don't work on private/final methods, final classes, or objects created directly with new.

Explain Dependency Injection in Magento 2. What are Factories, Proxies, Virtual Types?
"Magento 2 uses constructor injection configured through di.xml — you type-hint interfaces and the Object Manager injects the configured implementation. We never call the Object Manager directly in our code; it's used only by the framework and generated code.

A Factory is auto-generated code we inject when we need a new instance at runtime — for example a new OrderItem — because injecting the class directly would give a shared instance.

A Proxy is a lazy-loading wrapper — if a dependency is expensive (say a session or a heavy collection) and not always used, I declare a Proxy in di.xml so the real object is instantiated only on first use. Classic fix for slow CLI commands loading the session.

A Virtual Type lets me create a configured variant of an existing class purely in di.xml — different constructor arguments, no new PHP class — great for reusing something like a logger with a different handler."
What are Service Contracts and why do they matter?
"Service contracts are the module's public API — the Api folder: service interfaces like ProductRepositoryInterface and data interfaces like ProductInterface. Other modules, plugins, and web APIs should talk to these interfaces, never to concrete models or resource models. The benefit is stability: Adobe commits to backward compatibility on the API layer, so customisations built against contracts survive upgrades. They're also what gets exposed through webapi.xml as REST/SOAP endpoints automatically. In code reviews I flag any direct model usage where a repository exists."
Explain the EAV model. Why does Magento use it, and what's the trade-off?
"EAV — Entity, Attribute, Value — stores attributes in per-type value tables instead of columns: catalog_product_entity plus _varchar, _int, _decimal, _datetime, _text tables. Products, categories and customers are EAV; orders and quotes are flat tables because they're written once and read heavily.

The win is flexibility — merchants add attributes without schema changes, and values can differ per store view, which is how multi-language works. The cost is heavy joins on read. Magento compensates with indexers that flatten data for the storefront — like catalog_product_flat historically and price/eav indexes today — plus Elasticsearch/OpenSearch serving category and search listings."

Follow-up — attribute scope: global / website / store view. Price is website scope by default; name and description are store-view scope.

In production I run them in that order during deployment; in developer mode generation happens on the fly."

Follow-up — declarative schema vs InstallSchema: since 2.3, tables are declared in db_schema.xml and Magento diffs the declaration against the DB — idempotent and supports rollback of dropped columns via whitelist. Data changes go in data patches implementing DataPatchInterface with dependencies instead of version comparisons.

Layout XML, Blocks, ViewModels, UI Components — how does the frontend fit together?
"A page is assembled from layout XML handles — default.xml, then the page-specific handle like catalog_product_view.xml. Layout defines containers (structure) and blocks (content bound to a template). Modern practice is thin blocks with ViewModels for presentation logic, injected via layout arguments — better than overriding block classes. Theme resolution follows the fallback chain: my theme → parent theme(s) → module view files.

UI Components are the KnockoutJS-based system used for checkout, admin grids and forms — configured through XML and JS components. Checkout customisation is mostly a LayoutProcessor plugin plus a JS mixin or a custom component — for example adding a delivery-note field to the shipping step, saving it via an extension attribute on the quote."

Follow-up — add a field to checkout (classic!): LayoutProcessor plugin to inject the field into the jsLayout → knockout template renders it → on submit, pass via extension_attributes on shipping information → plugin/observer persists to quote table → fieldset.xml (sales_convert_quote) or plugin copies quote → order.

Commerce workflows (the JD explicitly lists these)

Walk me through what happens from "Place Order" to a completed order (tables included)
"Everything starts as a quote — the cart — in quote, quote_item, quote_address, quote_payment. On Place Order, checkout calls the payment method, and quote management converts the quote via sales_convert_quote mapping into sales_order, sales_order_item, sales_order_address, sales_order_payment, firing sales_order_place_after.

The order starts in Pending (or Processing if payment captured). An invoice records the money — sales_invoice — either capture-online for gateways like Adyen/Stripe or offline. A shipment (sales_shipment) records fulfilment with tracking; a credit memo handles refunds. Order state vs status: state is the internal machine (new, processing, complete, closed, canceled, holded); statuses are merchant-facing labels mapped to states.

With MSI, placing the order creates a reservation — stock is logically deducted through reservation entries and only physically deducted at shipment."
How do catalog price rules differ from cart price rules? Where do promotions fit?
"Catalog price rules change the displayed product price itself, before cart — applied by the price indexer on a schedule, based on attribute conditions. Good for 'flat 20% off category X this week'. Cart price rules apply at quote level during totals collection — coupon codes, buy-X-get-Y, free shipping — and can be limited by customer group, coupon usage, subtotal conditions. The totals pipeline collects subtotal → discounts → shipping → tax → grand total; custom fees are added by declaring a new total collector in sales.xml. On projects I've also handled promotion accuracy — on Surfline I maintained catalog pricing rules to keep promotions correct."
How does Multi-Source Inventory (MSI) work?
"MSI separates physical Sources (warehouses, stores) from logical Stocks, which map sources to sales channels (websites). Salable quantity is computed as the aggregate of assigned sources minus reservations — the append-only compensation records created at order placement. Physical deduction happens at shipment; cancellations append compensating reservations. The Source Selection Algorithm decides which source fulfils an order — by priority or distance. I worked hands-on with MSI on the Peelworks project, where inventory truth lived partly in the ERP, so understanding reservations was critical to keep both systems consistent."
Adobe Commerce vs Magento Open Source — what does the paid edition add?
"Open Source has the core platform. Adobe Commerce adds: B2B suite (company accounts, shared catalogs, requisition lists, quotes/negotiation), Content Staging & Preview for scheduled campaigns, customer segmentation & targeted rules, Page Builder (now also in OS but originated there), RMA, gift cards & store credit, Adobe Sensei-powered Product Recommendations & Live Search, Business Intelligence dashboards, and on Cloud: the managed hosting, Fastly CDN/WAF, staging/production environments and ece-tools deployment. For a consultant, edition choice is usually driven by B2B needs, content operations and support SLAs."

PHP & engineering quality (they will test "strong PHP" from the JD)

Rapid-fire PHP/OOP: interfaces vs abstract classes, traits, late static binding, strict types
  • Interface vs abstract class: interface = pure contract, multiple implementable; abstract class = partial implementation + state, single inheritance. Magento leans on interfaces for service contracts.
  • Traits: horizontal code reuse compiled into the class; use sparingly — Magento core barely uses them.
  • Late static binding: static:: resolves to the runtime class, self:: to the defining class.
  • Type system: declare(strict_types=1), scalar & return types, nullable types ?int, union types (PHP 8), constructor property promotion, readonly properties, enums (8.1). Mention you enforce these via SonarQube/code review — that's your Altimetrik story.
  • Design patterns you can name in Magento: Factory, Proxy (lazy), Observer, Interceptor/Decorator (plugins), Repository, Strategy (payment/shipping methods), Registry (deprecated!), Singleton-per-request via shared instances, Service Layer.
"At Altimetrik I lead our quality gate — SonarQube rules for PHP and JavaScript, standards from Magento's own coding standard ruleset, and code review before merge. I've personally driven cleanup of hundreds of static-analysis findings while keeping releases flowing."
Security: how do you keep a Magento store secure?
"Layers. Platform level: apply Adobe's security patches promptly — I track the security-only patch line so we can patch without taking a full version upgrade. Application level: output escaping with escapeHtml/escapeUrl against XSS, form keys against CSRF, ACL rules for every admin route and config section, never trusting input in custom APIs, and avoiding raw SQL in favour of the framework's prepared statements. Operational level: locked-down admin URL, 2FA (built-in since 2.4), least-privilege admin roles and integration tokens, reCAPTCHA on public forms, and a WAF — on Cloud that's Fastly. And code review as the last gate: I specifically look for unescaped output and missing ACL in every PR."

⚡ Performance, Caching, Indexing & Cloud

The JD explicitly says: "diagnose and resolve production issues, performance bottlenecks, and scalability concerns (caching, indexing, database, search)." This tab is that sentence, answered.

Explain Magento's caching architecture end-to-end (FPC, Varnish, Redis, private content)
"Top layer is full-page cache. In production that should be Varnish (or Fastly on Adobe Commerce Cloud), not the built-in FPC. Magento renders a page once, Varnish serves it to everyone after that.

The obvious problem: cart, customer name, wishlist differ per user. Magento solves it with private content — those blocks are rendered generic in the cached page, and the browser fills them via the customer-data JS library, which pulls JSON 'sections' (cart, customer) from the server and stores them in localStorage. sections.xml maps POST actions to sections that must invalidate — add to cart → cart section refreshes. Marking a block cacheable="false" in layout makes the entire page uncacheable — a classic performance bug I've actually fixed in the wild.

Below that: Redis for the config/block/layout caches and for sessions; cache tags let Magento invalidate precisely — saving a product purges only pages tagged with it. Cache types can be managed per type; in deployments we warm critical pages after flush rather than flushing blindly."

Likely follow-up — "page is not caching, how do you debug?" Check response headers (X-Magento-Cache-Debug in dev), look for cacheable="false" blocks in layout, check the page isn't a POST/customer-specific route, confirm Varnish VCL health, check marketing params are stripped/normalised.

Indexers: what are they, and what does "Update by Schedule" really do?
"Indexers pre-compute expensive derived data: price index, catalog rule index, category-product relations, stock, catalog search (feeding Elasticsearch/OpenSearch). Two modes: Update on Save reindexes synchronously on every save — fine for tiny catalogs, terrible at scale. Update by Schedule uses the mview mechanism: MySQL triggers write changed entity IDs into changelog tables (*_cl), and the indexer_update_all_views cron consumes them, reindexing only deltas. On any real catalog — like a client with frequent ERP price feeds — schedule mode is mandatory, otherwise imports crawl and admin saves block. I also know the ops side: bin/magento indexer:status, resetting a stuck 'processing' indexer, and watching changelog backlog size as a health metric."
A production Magento site is slow. Walk me through your triage. (Star question — rehearse!)
"First I split the problem: slow for everyone or some users, all pages or specific flows, since when — correlate with the last release or campaign start.

Then layer by layer. Edge: is Varnish/Fastly actually hitting — cache-hit ratio, or is everything MISSing because of a cookie or a cacheable="false" regression? App: New Relic (which I use daily at Altimetrik) — slowest transactions, worst DB queries, external calls blocking render, like a payment or ERP API called synchronously on a catalog page. DB: slow query log, missing indexes, table locks from a heavy import running in business hours. Search: Elasticsearch heap and query health. Infra: PHP-FPM worker saturation, Redis memory eviction, CPU steal.

Typical real causes I've fixed: uncacheable blocks, N+1 loading of products in a custom block instead of a collection/repository with proper joins, indexers left on Update-on-Save, cron pileups, and third-party modules doing external HTTP calls inline. Fix, measure, then add the regression guard — a dashboard alert or a code-review rule — so it can't come back silently."
Code-level performance rules you enforce as a lead
  • Never load models in loops — use collections/repositories with addFieldToFilter, select only needed attributes.
  • No getSize()/count() on huge collections when an EXISTS check works; paginate imports/exports; use generators for large datasets.
  • Push slow work off the request path: message queues / async operations for ERP calls, email, feed generation.
  • Frontend: critical CSS, defer JS, image lazy-load + WebP, minimise KO component bloat on checkout; measure with Lighthouse/CrUX.
  • Cron hygiene: dedicated groups, don't let one stuck job starve indexer group.
Adobe Commerce Cloud — what should a consultant know?
"Cloud is the managed PaaS: Pro has Integration / Staging / Production, with production a three-node HA cluster; Starter is simpler. Deployments are git-driven through ece-tools: build phase (composer, DI compile, static content) then deploy phase (config import, cache flush), configured in .magento.app.yaml, services.yaml and .magento.env.yaml. Fastly sits in front as CDN, image optimisation and WAF. Config should live in config.php/env variables — 'pipeline deployment' — so environments are reproducible. Logs and monitoring come with New Relic baked in. Even though my hands-on hosting has included on-prem and cloud VMs, the architecture maps one-to-one to what I already do: Varnish→Fastly, Redis, Elasticsearch, cron, deploy scripts — so I'm fully comfortable consulting on it."

Upgrades: how do you run a safe Magento version upgrade?
"I've done this end-to-end — I upgraded Tivoliwines from 2.1.18 to 2.3.5. My process: audit first — composer.json, all third-party modules and their compatibility, core overrides and preferences, then the Upgrade Compatibility Tool to surface breaking usage. 🔌 APIs & Integrations (Payments · Shipping · ERP · PIM)

The JD: "Drive integrations with third-party services (payments, shipping, tax, ERP/CRM, PIM) using REST/GraphQL and secure integration patterns." You have receipts for every word of that sentence.

REST vs GraphQL vs Async/Bulk — when do you use which?
"REST is the workhorse for system-to-system integration — ERP pushing products, OMS pulling orders. Routes are declared in webapi.xml, mapping a URL + HTTP verb to a service contract method with ACL. I've built these hands-on: on Peelworks I created custom REST modules including an order/product tracking API for the mobile app.

GraphQL is designed for the storefront — headless/PWA frontends query exactly the fields they need in one round trip; it's the API behind PWA Studio. Schema extension is via schema.graphqls plus resolvers.

For heavy write volume, the asynchronous and bulk REST endpoints queue requests into RabbitMQ and consumers process them — the right pattern for ERP pushing thousands of price/stock updates, instead of hammering synchronous endpoints.

Auth options: integration tokens for trusted server-to-server, OAuth for third-party apps, customer/admin tokens for user-scoped calls — with tokens scoped by ACL to the minimum needed."
Design an ERP ↔ Magento integration (you actually built one — lead with that!)
"I built exactly this at Neosoft for Peelworks — a module for two-way data synchronisation between Magento and the ERP. The design principles I apply:

Direction & ownership: decide the source of truth per entity — ERP owns products, prices, stock; Magento owns orders and customers. Never bidirectional ownership of the same field. Transport: deltas, not full dumps — timestamps or changelog-driven; queued via message queue or async bulk API so spikes don't hurt the storefront. Reliability: idempotency keys so retries don't duplicate orders; dead-letter handling with alerting; reconciliation job that compares counts/checksums daily to catch silent drift. Performance: batch updates, disable-then-reindex for large imports, run heavy syncs off-peak. Monitoring: a sync dashboard — last success, queue depth, failure count — because an integration you can't observe is an outage you'll discover from an angry customer."
How do you integrate a payment gateway? (Stripe, Adyen, PayUbiz, Paytm — all yours)
"I've integrated Stripe on Tivoliwines, PayUbiz and Paytm at Rightgifting, and I work with Adyen in my current project. Magento's modern way is the payment gateway framework: a payment method is configuration plus a chain of components — command pool (authorize, capture, void, refund), request builders that map order data to the gateway's API, an HTTP client, response handlers and validators. Frontend is a KO component feeding the payment info, ideally tokenising card data client-side so raw PAN never touches our server — that's the PCI boundary.

The parts people underestimate, which I always design for: webhooks/notifications — Adyen for example is notification-driven, so order state must be settled by the async notification, handled idempotently; edge states — payment captured but order save failed, duplicate notifications, partial refunds; and reconciliation against gateway reports. In my current project I've also debugged Adyen notification-cron issues in production, so I know the failure modes first-hand."
Message queues & crons — how does async processing work?
"Queues: a publisher pushes a message to an exchange, a topology routes it to a queue, a consumer processes it — configured via communication.xml, queue_topology.xml, queue_publisher.xml, queue_consumer.xml. Backend is RabbitMQ in production (MySQL-based queue exists but doesn't scale). Consumers run via queue:consumers:start, supervised by cron or a process manager.

Cron: jobs declared in crontab.xml in groups; schedule stored in cron_schedule. Ops knowledge that matters: stuck 'running' jobs blocking a group, missed schedules from an overloaded box, and cleaning the schedule table. I've debugged production cron issues — including payment-notification cron failures — using New Relic and logs."
Headless / PWA — what's your take as a consultant?
"Options: Luma (classic), PWA Studio or a custom React/Next storefront on GraphQL, or Adobe's newer Edge Delivery / drop-in components direction. My consulting view: headless buys frontend velocity and Lighthouse scores, but costs you the ecosystem — many extensions assume Luma, so every third-party feature needs frontend rebuilding. I recommend headless when the client has a strong frontend team and a differentiated UX vision; I recommend optimised Luma/Hyvä-style approaches when time-to-market and extension leverage matter more. The right answer is a TCO conversation, not a fashion choice."

🏗️ Consultant-Level Scenarios (Round 2 Gold)

"Consultant" means: ask clarifying questions → structure the answer → give options with trade-offs → recommend. Practise saying these frameworks out loud.

"A client wants a new Adobe Commerce store. How do you run discovery & estimation?"
"Discovery first, in four buckets. Business: B2C or B2B, markets/languages/currencies, order volume, peak events. Catalog: SKU count, configurable/bundle complexity, who owns product data — is there a PIM? Integrations: ERP, OMS, payment providers, tax, shipping carriers, CRM, analytics. Non-functional: performance targets, compliance, launch date, budget guardrails.

Then I decompose into epics — catalog, checkout & payments, integrations, theme/UX, data migration, infra & launch — and estimate each with the team using story points or three-point estimates, adding explicit risk buffer on integrations and migration because that's where surprises live. Output: a phased plan — MVP launch scope versus fast-follow — because my strong recommendation is always to launch a smaller scope earlier and iterate. I present estimates with assumptions written down; an estimate without assumptions is a future dispute."
"Client's checkout conversion dropped after last release. What do you do?"
"Treat it as an incident. First quantify: which step of the funnel drops — analytics tells me if it's cart→shipping, shipping→payment, or payment failures. Cross-check New Relic and browser errors: a JS error in a checkout KO component often breaks silently for a segment — one browser, one payment method, guest vs logged-in. Then diff the release: what touched checkout, payment configs, or shipping rates? If a payment method's error rate spiked, check the gateway dashboard before blaming code — sometimes it's the PSP. Mitigation before root cause if revenue is bleeding: feature-flag off or roll back the offending change — which is why I insist releases are small and rollback-able. Afterwards: postmortem, and a synthetic checkout monitor so the next regression pages us before customers feel it."
"Design a multi-country rollout (5 countries, 3 currencies, 2 languages each)."
"Magento hierarchy: Websites → Stores → Store Views. My default: one website per country — that gives separate base currency, pricing, tax, payment and shipping config per country — with store views per language. Shared catalog with per-website price scope, or per-country catalogs if assortments truly differ. Key decisions I'd surface: single Adobe Commerce instance versus regional instances (latency + ops trade-off), tax and invoicing compliance per country, payment method mix per market — local methods matter for conversion — domain strategy and hreflang for SEO, and a content-operations model so marketing can run country campaigns without dev tickets — Content Staging helps there. I'd pilot with one country, template the setup, then stamp out the rest."
"1 million SKUs need to be imported nightly from a PIM. Architecture?"
"First push back on the requirement: does the full million change nightly? Almost never — so delta sync, full load only as recovery. Transport via async bulk API or direct queue consumers. Import path optimised: batched operations rather than row-by-row saves, indexers on schedule and reindexed after the batch, cache invalidation targeted by tags rather than a full flush. Media offloaded to CDN, downloaded async. Guardrails: validation quarantine for bad rows so one broken record doesn't kill the batch, run-duration alerting, and a reconciliation count at the end. And I'd run it against staging first with production-scale data — import performance only shows its problems at real volume."
"How do you define technical standards for a team?" (JD bullet, verbatim)
"I do this today. Three layers. Automated: SonarQube quality gates plus Magento coding-standard PHPCS in CI — at Altimetrik I drove our SonarQube adoption and personally burned down the backlog across PHP and JavaScript. Process: mandatory peer review with a checklist — service contracts over model access, plugin over preference, ACL on every route, output escaping, no logic in templates; definition-of-done includes tests and doc notes. Human: I mentor rather than gatekeep — at Xperi I trained junior developers and documented workflows for new joiners, because a standard that lives only in review comments dies. Standards stick when the team understands the 'why'."
"An extension vendor's module conflicts with your customisation. Client is blocked. Go."
"Diagnose precisely: plugin list on the disputed method (bin/magento dev:di:info), who wins on preference, what sortOrder collision exists. Short-term unblock: adjust plugin sortOrder or scope our plugin more narrowly. Right fix: if the vendor module is at fault, open a vendor ticket with a reproducible case, and carry a composer patch until their fix ships — patches tracked in version control, re-validated each upgrade. Never fork a vendor module silently; that's an upgrade time-bomb. And I log the decision in the project's ADR so the next team knows why the patch exists."
"Production is down on a sale day. Walk me through your incident leadership."
"Roles first, panic never: one person communicates to stakeholders — status every 30 minutes even if the status is 'still investigating' — while I drive diagnosis. Check the obvious fast: last deploy? traffic spike? infra alarm? payment provider down? Restore service before root-causing: roll back, scale out, serve cached, or gracefully degrade — disable a heavy feature to keep checkout alive; checkout availability is the only KPI during a sale. Afterwards: blameless postmortem, and every incident buys us a permanent improvement — an alert, a runbook line, a capacity fix. I've done production triage with New Relic in my current role, so this isn't theory for me."
