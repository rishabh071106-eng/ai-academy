REST API Actions: The Verbs Your Agent Speaks

GET, POST, PUT, PATCH, DELETE — the handful of actions every REST API is built from, and why an AI agent has to get them right.

We've spent a few chapters on how an AI model reaches out and touches the world: function calling lets it request an action, and an orchestrator turns that request into a real API call. But what does the API on the other end actually understand? When your agent "calls an API," it's almost always speaking a small, fixed vocabulary of actions. Five of them do ninety-five percent of the work.

If you want to build agents that don't accidentally delete a customer record while trying to read it, you need to know these verbs cold. The good news: there are only a few, and they map onto things you already do every day.

One URL, Several Things You Can Do To It

REST is built on a simple idea. Everything is a resource — a user, an order, a document — and each resource lives at an address called a URL, like /users/42. The clever part is that the same address supports several different actions, and which action you want is carried by the HTTP method (also called the verb).

Think of a resource as a house at a street address. The address never changes. But you can do different things there: look through the window (read), move in (create), gut-renovate (replace), swap the couch (partial update), or demolish it (delete). Same address, very different intentions.

The URL says what you're acting on. The method says what you're doing to it. Get those two right and you've understood most of REST.

The Five Actions You'll Actually Use

Here's the whole working vocabulary, in plain terms.

GET — read it. Fetch a resource without changing anything. GET /users/42 returns user 42. GET /users returns the list. A GET should never modify data — it's the one verb you can fire a thousand times with zero consequences.

GET /users/42
→ 200 OK
{ "id": 42, "name": "Ada", "role": "admin" }

POST — create something new. You send data, the server creates a new resource and usually assigns it an ID. POST /users with a body makes a new user. Run it twice and you get two users — POST is not repeatable without side effects, which matters more than it sounds.

POST /users
{ "name": "Grace", "role": "engineer" }
→ 201 Created
{ "id": 43, "name": "Grace", "role": "engineer" }

PUT — replace it whole. You send the complete new version of a resource, and the server overwrites what's there. PUT /users/42 with a full object replaces user 42 entirely. Anything you leave out of the body may be wiped — PUT means "make it look exactly like this."

PATCH — change part of it. You send only the fields you want to change. PATCH /users/42 with {"role": "viewer"} updates just the role and leaves the name alone. PATCH is the scalpel; PUT is the sledgehammer.

PATCH /users/42
{ "role": "viewer" }
→ 200 OK   (name untouched, role changed)

DELETE — remove it. DELETE /users/42 deletes user 42. Straightforward, and the one you most want an agent to pause before calling.

💡
The cheat sheet: GET reads, POST creates, PUT replaces, PATCH edits, DELETE removes. If you ever map these onto a database, they line up almost exactly with the classic CRUD operations — Create, Read, Update, Delete.

Two Properties That Keep Agents Safe

Beyond knowing the verbs, there are two ideas the spec hangs on the verbs — and they're exactly the properties that decide whether a retry is harmless or catastrophic. This is where it stops being trivia and starts mattering for autonomous systems.

Safe methods don't change anything. GET (and its cousins HEAD and OPTIONS) are "safe": calling them has no side effects. An agent can explore freely with GET, caching results, retrying on timeouts, fanning out in parallel — none of it can hurt.

Idempotent methods give the same result no matter how many times you call them. This is the one that bites people. PUT and DELETE are idempotent: deleting user 42 once or five times leaves the same end state (gone). GET is idempotent too. But POST is not — call "create order" twice and you've charged the customer twice.

Why does an AI agent care? Because agents live in an unreliable world of timeouts and retries. When a call fails halfway, the safe move is to retry — but only if the action is idempotent. Retrying a GET or a DELETE is fine. Blindly retrying a POST can double-book a flight. Mature systems handle this with an idempotency key: the agent attaches a unique ID to a POST, and the server promises to process it only once even if the request arrives twice.

The single most useful thing to internalize: GET and DELETE and PUT are safe to retry; POST is not. Design your agent's error handling around that line.

The Server Talks Back: Status Codes

Every action gets an answer, and the answer leads with a three-digit status code. You don't need all of them, just the families:

  • 2xx — it worked. 200 OK (here's your data), 201 Created (new resource made), 204 No Content (done, nothing to return — common after DELETE).
  • 4xx — you messed up. 400 Bad Request (malformed input), 401/403 (not authenticated / not allowed), 404 Not Found (no such resource), 429 Too Many Requests (slow down).
  • 5xx — the server messed up. 500 (it crashed), 503 (temporarily down). These are the ones worth retrying with backoff.

For an agent, the status code is the feedback signal. A 404 means "stop, this doesn't exist." A 429 or 503 means "wait and try again." A 400 means "fix the arguments you generated and don't just retry the same thing." Teaching a model to read these and react correctly is a real part of building reliable tool use — it's the same loop we talked about in function calling, just with the API's reply as the input.

The Two You'll Meet Less Often

For completeness: HEAD is like GET but returns only the headers, no body — handy for checking "does this exist?" or "how big is it?" without downloading it. OPTIONS asks the server which methods a resource supports, and it's what your browser quietly fires before a cross-origin request (the "CORS preflight"). You'll rarely call these by hand, but it's good to recognize them when they show up in logs.

Why This Belongs in an AI Course

It's tempting to file HTTP verbs under "boring web plumbing." But the entire premise of agentic AI is models that act — and out in the real world, acting means making these exact calls. When you write a tool definition for a model, you're really wrapping one of these actions: a "search products" tool is a GET, a "place order" tool is a POST, a "cancel subscription" tool is a DELETE.

The same caution we apply to giving a model dangerous tools applies here, verb by verb. Reads are cheap and safe; let the agent do them freely. Writes and deletes change the world and often can't be undone; gate them behind validation, confirmation, or human approval. Half of building a trustworthy agent is just knowing which verb a given action is, and treating it accordingly.

A few principles to carry forward:

  • Match the verb to the intent. Reading? GET. Creating? POST. Editing one field? PATCH, not PUT. Using the wrong verb is how data quietly gets clobbered.
  • Respect idempotency on retries. Retry GET, PUT, and DELETE freely. Guard POST with an idempotency key before you ever let an agent retry it.
  • Treat status codes as instructions. 4xx means change something; 5xx and 429 mean wait and retry; 2xx means move on.
  • Put a fence around destructive verbs. DELETE and overwriting PUTs deserve a confirmation step, especially when a model is the one deciding to call them.

That's the whole vocabulary. Five everyday verbs, two safety properties, and a handful of status codes — and with them you can describe almost any action an AI agent will ever take against the outside world.
