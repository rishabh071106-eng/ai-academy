Function Calling: How AI Learned to Use Tools

The mechanism that turns a chatbot into something that can actually do things in the real world.

You already know that agentic AI is about models that take actions, not just produce text. But we glossed over the core mechanism that makes action possible. How does a language model—a thing that predicts the next token—actually call an API, query a database, or send an email?

The answer is function calling, sometimes called tool use. It's less glamorous than it sounds, and more clever than you'd expect.

The Fundamental Problem

An LLM generates text. That's it. It cannot execute code, make HTTP requests, or touch a database. It lives in a padded room made of tokens.

So when you ask ChatGPT to check the weather, the model doesn't somehow reach out to a weather service. Instead, it outputs a very specific, structured piece of text that describes which function it wants to call and what arguments to pass. Then a separate piece of software—the orchestration layer—reads that structured output, actually calls the weather API, and feeds the result back to the model for a final, human-friendly response.

Function calling is the model raising its hand and saying, "I'd like someone to run this function with these parameters." It never runs anything itself.

This distinction matters. The model is still just predicting tokens. But it's been trained (or prompted) to predict tokens in a very particular format when it recognizes that a tool would help.

How It Works, Step by Step

Let's trace a concrete example. You send a message: "What's the weather in Tokyo right now?"

Step 1: Tool definitions go in. Before your message reaches the model, the system includes a list of available tools in the prompt—usually as a JSON schema. Something like:

{
  "name": "get_weather",
  "description": "Returns current weather for a city",
  "parameters": {
    "type": "object",
    "properties": {
      "city": { "type": "string" },
      "units": { "type": "string", "enum": ["celsius", "fahrenheit"] }
    },
    "required": ["city"]
  }
}

The model now knows a tool called get_weather exists, what it does, and exactly what arguments it accepts.

Step 2: The model decides to call a tool. Instead of generating a natural language answer (which would be a hallucinated guess), the model outputs structured JSON:

{
  "function_call": {
    "name": "get_weather",
    "arguments": { "city": "Tokyo", "units": "celsius" }
  }
}

This is the key moment. The model chose the right tool and extracted the right arguments from your casual, human question. No code was executed—just structured text.

Step 3: The orchestrator executes the call. Your application code sees this structured output, calls the actual weather API, and gets back real data: {"temp": 22, "condition": "partly cloudy"}.

Step 4: The result goes back to the model. The orchestrator injects the API response into the conversation as a new message, and the model generates its final reply: "It's 22°C and partly cloudy in Tokyo right now."

Four steps. Two round trips to the model. One actual API call in between. That's the whole trick.

Why This Is Harder Than It Looks

The elegance of the pattern hides real engineering challenges.

Choosing the right tool. Give a model three tools and it performs well. Give it thirty and it starts making questionable choices—picking a similar-sounding function, hallucinating parameters, or calling tools when it shouldn't. This is why tool descriptions are a form of prompt engineering. Vague descriptions lead to vague decisions.

Argument extraction. The model has to parse your natural language into typed, structured arguments. "What's the weather in Tokyo" is easy. "How about there?" when you mentioned Tokyo three messages ago? That requires the model to resolve context across the conversation—something it's surprisingly good at, but not perfect.

Chaining calls. Real tasks rarely need one tool. Booking a trip might require searching flights, checking your calendar, comparing prices, and then making a reservation. Each call's output feeds into the next call's input. This is where function calling becomes agentic—the model is planning a multi-step sequence. And this is also where things can go sideways, because errors compound.

Parallel calls. Sometimes you need to call multiple tools at once—weather in Tokyo and the current exchange rate. Modern function calling APIs (OpenAI, Google Gemini, Anthropic) now support parallel tool calls in a single model response, which cuts latency significantly.

The Ecosystem Is Converging

A year ago, every provider had a different approach. OpenAI had its function calling API, Anthropic had tool use with a slightly different schema, and open-source models were largely fending for themselves. That's changing.

There's now rough consensus on the pattern: you define tools with JSON Schema, the model outputs structured calls, and you handle execution. The Hugging Face team recently published a piece on getting agent terminology right—distinguishing "harness" from "scaffold"—which reflects how the community is maturing past the hype into precise engineering vocabulary.

💡
Fun fact: The term "function calling" is slightly misleading. The model never calls a function. A more accurate name would be "function requesting"—but that ship has sailed.

For open-source models, tool use capability increasingly comes from fine-tuning on datasets of tool-use conversations. Models like Llama and Mistral variants now ship with tool-use training baked in, so you don't have to rely on fragile prompt hacks to get structured output.

What This Means for You

If you're building anything with AI that touches the real world—fetching data, triggering workflows, modifying records—function calling is the interface layer you need to understand. It's not optional plumbing. It's the bridge between language and action.

A few practical principles worth remembering:

  • Fewer tools, better results. Don't give the model a Swiss Army knife with 50 blades. Curate a focused set of tools for each task.
  • Descriptions are critical. The model picks tools based on their descriptions, not their implementation. Write them like you're explaining the tool to a smart colleague.
  • Validate everything. The model's output is a suggestion. Your code should validate arguments, handle errors, and never blindly trust the model's choices—especially for destructive operations.
  • Think about the loop. The power isn't in a single call. It's in the feedback loop: model decides, tool executes, result returns, model continues. Design your system around that cycle.

Function calling is one of those ideas that seems almost too simple when you first see it. A language model outputs JSON instead of prose, and suddenly it can interact with the world. But that simplicity is the point. By keeping the model's role narrow—decide what to call, not how to execute it—you get a system that's composable, auditable, and much easier to reason about than letting an AI loose with a code interpreter and a prayer.
