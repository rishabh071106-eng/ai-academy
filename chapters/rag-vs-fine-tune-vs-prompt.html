RAG vs fine-tune vs prompt

The three ways to make an LLM "know" your data. Most people pick wrong on the first try. Here's the framework I wish I'd had.

You want to build an AI product. You have your company's docs, customer support history, an internal wiki, a product manual. The model hasn't seen any of it. How do you make it useful?

Three options. They are not interchangeable. Picking the wrong one wastes months.

Option 1: Just prompting (including the docs)

The simplest: paste your data directly into the prompt. Called "in-context learning."

Here is our company's return policy:
{entire policy doc}

A customer asks: "{user question}"
Answer using only the policy above.

When it's the right call:

  • Data fits comfortably in the context window (say, under 50,000 tokens)
  • Same data is relevant to every query
  • You want to ship tomorrow, not next quarter

When it breaks:

  • You have 10,000 pages of docs. Can't fit.
  • You'd be paying to re-send the same docs on every API call. Expensive.
  • Different queries need different docs. No way to route.

Option 2: RAG (Retrieval-Augmented Generation)

Instead of pasting all your docs every time, you:

  1. Chop your docs into small chunks (a few hundred words each)
  2. Turn each chunk into an embedding (remember Chapter 2?) and store them in a vector database
  3. When a user asks something, turn their question into an embedding too
  4. Find the top 3-10 chunks whose embeddings are closest to the question
  5. Paste only those chunks into the prompt, then ask the model

Essentially: a Google-for-your-docs, but using semantic similarity instead of keywords, plumbed into the LLM.

🔎
Why RAG is the default for enterprise AI: it scales to any amount of data, lets you update the knowledge base without retraining anything, and gives you citations — you know exactly which chunks the answer was based on.

When it's the right call:

  • You have a lot of documents, frequently updated
  • You need the model to answer based on specific, factual material
  • You want to cite sources
  • You're building a Q&A, search, or support assistant

When it's overkill:

  • Your data fits in one prompt — just paste it
  • You need the model to sound a certain way (that's fine-tuning)
  • You need deep reasoning over many chunks at once (RAG struggles with this)

Option 3: Fine-tuning

You take a base model and keep training it — with additional examples of the behavior you want. You're not teaching it facts, you're teaching it patterns: style, format, domain-specific vocabulary, new types of tasks.

Think of it as: prompting is instruction, RAG is giving the model a library card, fine-tuning is sending the model to specialized school.

When it's the right call:

  • You need consistent, specific output style or format that few-shot can't reliably produce
  • You're running at scale and want to cut costs by using a smaller model that's been fine-tuned to match a bigger one's output
  • You have a very specialized task (medical code generation, legal clause drafting) where generic models underperform

When it's the wrong call (which is most of the time):

  • You want the model to "know" your docs → use RAG. Fine-tuning is bad at learning facts.
  • You haven't maxed out prompting yet → do that first
  • Your data is small (under a few thousand good examples) → not worth it
  • Your data changes often → you'd be fine-tuning constantly. Use RAG.

The decision tree

  1. Can I solve this with better prompting? → Do that. Done in a day.
  2. Does the model need access to specific documents? → RAG.
  3. Does the model need to consistently speak/format/behave in a very specific way that prompting can't achieve reliably? → Fine-tune.
  4. Need all three? Then do all three. They compose. (Advanced systems often fine-tune for format, RAG for knowledge, and prompt carefully at inference.)

The expensive mistake

The #1 mistake teams make: they hear "fine-tune our data into the model" and spend six months collecting a dataset, only to find the output is indistinguishable from what good prompting + RAG would've gotten them in two weeks.

Fine-tuning is where you go when prompting and RAG have failed you — not the first stop.

Quick comparison

                    Prompting   RAG     Fine-tune
Setup time          minutes     days    weeks+
Cost per query      medium      medium  low (small model)
Up-front cost       $0          $100s   $1000s
Updates knowledge   trivial     easy    retrain
Changes style/tone  limited     no      yes
Cites sources       no          yes     no
Max data size       context     any     (training set)

Start with prompting. Go to RAG when you outgrow prompting. Go to fine-tuning only when you have a specific reason the other two can't meet.
