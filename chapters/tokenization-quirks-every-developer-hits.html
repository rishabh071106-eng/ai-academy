Tokenization Quirks Every Developer Hits

Why your model can't spell 'strawberry,' and other mysteries of how text becomes numbers.

The Invisible Translation Layer

You already know that LLMs don't read words. They read tokens—chunks of text converted to numbers. You've probably nodded along to that explanation and moved on. But the specific way text gets carved into tokens explains a surprising number of the weird behaviors you've encountered: bad math, mangled spelling, inconsistent pricing across languages, and prompts that mysteriously blow your context window.

Tokenization isn't glamorous. It's plumbing. But like actual plumbing, you don't think about it until something starts leaking.

How "Strawberry" Breaks Your Model

Ask GPT-4 how many r's are in "strawberry" and it famously struggles. This isn't because the model is bad at counting. It's because the model never sees individual letters. A BPE (Byte-Pair Encoding) tokenizer might split "strawberry" into something like ["str", "aw", "berry"]. The model sees three tokens, none of which cleanly isolate the letter "r." It's trying to count characters inside opaque chunks it treats as atomic units.

This is the fundamental quirk: the unit of meaning for the model is the token, not the character and not the word. Anything that requires character-level reasoning—anagrams, spelling checks, simple regex-like tasks—forces the model to work against its own perception.

Asking an LLM to count letters in a word is like asking you to count the number of times the letter "e" appears in a paragraph—but the paragraph is written in Morse code. You can do it. It's just not what the representation was optimized for.

The Quirks That Actually Bite You

Here are the tokenization surprises that trip up developers in practice, not just in party tricks:

1. Whitespace is part of the token

Most tokenizers attach leading whitespace to the following token. The token for " hello" (with a space) is different from "hello" (without). This means your few-shot examples can behave differently depending on whether you left a trailing space in your prompt. I've seen developers debug prompt regressions for hours before realizing they'd reformatted their template and introduced an extra newline.

2. Numbers are tokenized inconsistently

The number "12345" might become ["123", "45"] or ["1", "234", "5"] depending on what appeared in the training data. This is one reason LLMs are shaky at arithmetic—the digit boundaries don't align with token boundaries. The number 380 and the number 3800 might share a token prefix, making them seem "closer" to the model than 380 and 381.

3. Non-English languages burn more tokens

BPE vocabularies are built from training data, which skews heavily English. A sentence in Japanese or Hindi can use 2-4x more tokens than its English equivalent. This isn't just an efficiency problem—it means your context window effectively shrinks for non-English users, and API costs go up per semantic unit. If you're building a multilingual product and budgeting by token count, you're implicitly giving English-speaking users more capability per dollar.

4. Code tokens aren't what you think

Indentation in Python gets its own tokens. A four-space indent and a tab are different tokens. Common variable names like self or index are single tokens, but your custom variable mySpecialCounter might split into three or four. This means the model "understands" standard coding conventions more fluently than your project's idiosyncratic naming—which is actually a reasonable argument for conventional naming in AI-assisted development.

💡
You can see exactly how any text tokenizes using OpenAI's online tokenizer tool or Hugging Face's tokenizers library. Spending ten minutes pasting your actual prompts into one of these tools is worth more than reading five articles about tokenization (including this one).

What You Can Actually Do About It

You can't change how a model tokenizes. But you can work with the grain instead of against it:

For counting and character-level tasks, ask the model to first spell out the word letter by letter. Forcing it to generate s-t-r-a-w-b-e-r-r-y gives it individual tokens for each character, turning an impossible task into a straightforward one. This is a chain-of-thought trick, but it works specifically because it changes the token-level representation.

For cost and context management, count tokens, not words. The rule of thumb "one token ≈ ¾ of a word" is fine for English prose and dangerously wrong for code, structured data, or non-Latin scripts. Use tiktoken or your model's actual tokenizer to count precisely.

For prompt stability, be consistent with formatting. Same whitespace, same delimiters, same casing. Token boundaries shift with seemingly trivial formatting changes, and those shifts can cascade into different model behavior. If you're versioning your prompts (and you should be), treat whitespace changes as meaningful diffs.

For multilingual applications, test token counts across all your supported languages early. I've seen teams discover mid-launch that their carefully tuned system prompt plus user input exceeded the context window—but only in Korean.

The Bigger Picture

Tokenization is one of those areas where the research community knows it's a compromise. BPE was borrowed from data compression in the 1990s and adapted for neural networks. It works well enough that it's become the default, but "well enough" papers over real limitations. There's active work on tokenizer-free models that operate on raw bytes, and on tokenizers with much larger vocabularies that handle multilingual text more equitably.

Hugging Face recently announced work on designing their CLI as an agent-optimized interface—a reminder that as we build more agentic systems, these low-level details compound. An agent that chains multiple LLM calls together amplifies every tokenization quirk across each step. A subtle whitespace issue in one call's output becomes a different token sequence in the next call's input.

For now, the practical takeaway is simple: the model doesn't see what you see. It sees tokens. And once you internalize that—really internalize it, not just nod along—a lot of previously mysterious LLM behavior starts making perfect sense.
