Embeddings: How Machines Actually Understand Meaning

Forget keyword matching — embeddings let AI search by what you mean, not what you typed.

The Problem With Ctrl+F

You know this frustration. You search your company's knowledge base for "employee vacation policy" and get zero results — because the document is titled "PTO Guidelines." You used the wrong words. The meaning was identical. The machine didn't care.

Traditional search is string matching with extra steps. Even fancy versions (stemming, synonyms, TF-IDF scoring) are still fundamentally asking: do these characters appear in that document?

Embeddings flip the question entirely. Instead of matching words, they match meaning. And once you see how they work, you'll understand a quiet piece of infrastructure behind almost every AI application you've read about in this series — including RAG, which we covered a few chapters back.

Turning Words Into Coordinates

An embedding is a list of numbers — a vector — that represents where a piece of text sits in "meaning space." A sentence, a paragraph, an entire document: each gets compressed into something like 768 or 1,536 floating-point numbers.

Think of it like GPS coordinates, but instead of two dimensions (latitude and longitude), you have hundreds. Each dimension captures some fuzzy aspect of meaning. No single number means "this text is about food" or "this text is angry." But taken together, the full vector places the text at a precise location in a high-dimensional space where similar meanings cluster together.

So "employee vacation policy" and "PTO guidelines" end up near each other. "How to bake sourdough" ends up very far away from both. The distance between two vectors — typically measured by cosine similarity — becomes a proxy for semantic relatedness.

An embedding doesn't store what a text says word by word. It stores roughly what it's about and how it feels — compressed into a point in space. Search becomes: find the nearest points.

How Embedding Models Are Made

You don't hand-craft these vectors. A neural network learns them. The training process is clever: show the model millions of pairs of texts that are related (a question and its answer, a paragraph and its summary) and train it so that related pairs produce vectors close together, while unrelated pairs drift apart.

The result is a model — separate from the LLMs you already know — whose only job is to take text in and push a vector out. OpenAI has one. Cohere has one. There are excellent open-source options on Hugging Face. Google just showed off new Gemini capabilities at I/O 2026, and embeddings remain a foundational part of their AI stack even as the flashy demos focus on multimodal generation.

These models are small and fast compared to a full LLM. Encoding a sentence takes milliseconds. That speed matters, because you're going to encode a lot of text.

The Pipeline: From Documents to Answers

Here's how semantic search actually works in practice:

  1. Chunk your documents. Break them into passages — maybe 200-500 tokens each. Too big and the meaning gets diluted. Too small and you lose context.
  2. Embed each chunk. Run every passage through the embedding model. Store the resulting vectors in a vector database (Pinecone, Weaviate, Chroma, pgvector — there are many).
  3. Embed the query. When a user searches, run their question through the same model to get a query vector.
  4. Find nearest neighbors. The vector database returns the chunks whose vectors are closest to the query vector.
  5. Return or feed to an LLM. You can show the results directly, or — and this is where it connects to RAG — stuff those top chunks into an LLM's prompt as context for generating an answer.

That's the whole thing. Step 2 is a one-time cost (plus updates when documents change). Steps 3-5 happen in real time, usually in under a second.

💡
Fun fact: The math for finding nearest neighbors in high-dimensional space is genuinely hard. Vector databases use approximate algorithms (like HNSW) that trade a tiny bit of accuracy for massive speed gains. You might miss the 7th-best result. You'll almost always get the top 3. For search, that tradeoff is excellent.

Where This Breaks (and What Helps)

Embeddings aren't magic. They have real failure modes worth knowing about.

Ambiguity gets flattened. The word "bank" in "river bank" and "bank account" produces different embeddings in context — modern models handle this well. But subtle distinctions can still collapse. A passage criticizing a policy and a passage endorsing the same policy might land suspiciously close together, because they're about the same topic.

Length mismatch matters. Embedding a five-word query and comparing it to a 300-word passage is asking the model to do a slightly awkward comparison. Some models (like Cohere's or the E5 family) are specifically trained to handle asymmetric queries and documents. Others struggle.

Domain specificity. A general-purpose embedding model trained on web text may not understand that "PT" in a medical context means "physical therapy" not "personal training." Fine-tuning an embedding model on your domain data — which is cheaper and faster than fine-tuning an LLM — can dramatically improve results.

The best production systems often combine semantic search with traditional keyword search (a technique called hybrid search) and then use a small reranking model to sort the merged results. Belt, suspenders, and a well-placed safety pin.

Why This Is the Infrastructure Layer

If you've been following this series, you might notice embeddings quietly sitting beneath several topics we've already covered. RAG? It's built on embedding-based retrieval. Agentic AI? Agents use vector search to pull relevant context before acting. Even fine-tuning decisions start by asking: can we just retrieve the right information instead?

Embeddings aren't glamorous. Nobody puts "powered by cosine similarity" on their landing page. But they've become one of the most practical, most deployed pieces of the modern AI stack — the layer that connects your messy, specific, private data to the general intelligence of a language model.

Next time you type a natural-language question into any AI-powered search box and it just works, despite you using none of the "right" keywords — now you know what's happening underneath. Your words became coordinates. The nearest neighbors came back. And the distance between your question and its answer turned out to be surprisingly small.
