Agentic AI: when AI uses tools

An LLM that can browse the web, run code, and call APIs isn't a chatbot anymore. It's something qualitatively new — and everyone's still figuring out how to use it.

A plain LLM is a text function. You give it text, you get text back. Useful, but limited. It can't check the weather. It can't send an email. It can't read a file on your computer. It can't even check if its own answer is correct.

An agent is an LLM plus a set of tools it can choose to call. That small shift changes almost everything.

The core mechanic

You give the model a list of "tools" it can use — each one is essentially a function with a name, description, and parameters. Something like:

Tools available:
- search_web(query: string)
- read_file(path: string)
- send_email(to: string, subject: string, body: string)
- run_python(code: string)

Then the model, instead of just replying in text, can choose to emit a "tool call" — a structured request like "call search_web with query='weather in Bengaluru today'." Your system actually runs that function, feeds the result back to the model, and the loop continues.

The model is still just predicting tokens. But now some of those tokens cause real-world actions.

⚙
The loop: user asks → model plans → model calls tool → tool runs → result goes back to model → model calls another tool or answers. This runs until the model decides it's done.

Why it's a big deal

A plain LLM can tell you, from training data, how to book a flight. An agent with a browser tool and an airline API can actually book the flight.

The difference isn't incremental. It's the difference between:

  • A book on plumbing vs. a plumber
  • A recipe vs. a chef
  • A tutorial on React vs. an engineer who can just build you the app

For two decades, software was something humans wrote and ran. Agents make it possible for software to be something a model writes and runs, while you watch.

What can agents actually do today?

Real, working, in-production examples as of 2026:

  • Coding: Claude Code and similar can read a codebase, write a feature, run the tests, debug failures, and commit the fix.
  • Research: Given a question, browse many sources, synthesize, cite. (Like this very site's content pipeline.)
  • Customer support: Look up the order, check the refund policy, issue the refund, email the customer.
  • Data analysis: Query a database, run calculations in Python, build charts, write a narrative report.
  • Ops automation: Read a ticket, determine the root cause, apply the fix, close the ticket.

Three things that make or break an agent

1. The tools you give it

Bad tools → useless agent. Good tools are: well-named, narrowly scoped, return structured output, fail clearly. "search_web" is vaguer than "search_company_docs(query, department)". Specific tools produce specific, reliable behavior.

2. The guardrails

An agent with tools can do real damage. Delete files. Send emails. Spend money. Every production agent needs:

  • Whitelist of allowed actions
  • Approval gates on anything irreversible
  • Logs of every tool call
  • Spending / time limits (they can loop forever if you let them)

3. The task decomposition

Agents are good at short, bounded tasks. They degrade as tasks get longer. The trick is breaking a big goal into small steps and giving the agent clear exits. "Book me a flight" fails often. "Given these 3 valid flights, pick the cheapest and book it" succeeds reliably.

The honest limitations

Despite the hype, agents today fail at a lot. Real failure modes you'll hit:

  • Forgetting their own plan. On long tasks, the agent's early instructions drift out of context.
  • Over-tooling. Given many tools, agents get confused about which to use.
  • Prompt injection. If an agent reads a web page, and that page contains instructions, it may follow them. This is a real and unsolved security problem.
  • Confident failure. They will claim success when they've failed. Always verify, never trust.
  • Cost escalation. A buggy agent that loops can burn through $100 in API calls in minutes.

How to think about agents practically

If you're building: narrow agents beat general ones, every time. A "reply to support ticket" agent with 3 tools is worlds more reliable than a "do anything" agent with 30. Start narrow. Expand slowly.

If you're using: the best agents today work with you, not instead of you. You're the verifier. The model does 80% of the boring part, you do the final 20% of judgment and quality control. That's where the productivity leap is.

The 2020s AI promise wasn't "AI that replaces you." It was "AI that lets one of you do the work of five." That promise, narrowly scoped, is real.
